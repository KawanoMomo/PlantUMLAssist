## ECN-030 (契約経路の欠陥) — 要検討

05 で12例出た archetype は、いずれも「UI は生の関数を直接呼び、契約経路が
古いまま残る」ことが原因だった。**06 は 6モジュール中1つしか `operations` を
持たないので、同じ形はまだ発生しにくい**。ただし裏返すと、
**契約を導入する段で同じ罠に入る**。

| archetype | 06 での状況 | 判定 |
|---|---|---|
| (1) id 認識の関数はあるのに入口が繋がっていない | 契約が sequence のみ。他5モジュールは今後導入される | **要検討** — 導入時に「入口から id を渡す」ことを最初から規約にする |
| (2) 行の中身で分岐して別の要素を編集する | PlantUML も `A -> B : msg` のように**1行が複数の宣言を兼ねる**書き方が普通。同じ罠がある | **要検討** — 分岐は `opts.kind` で行う |
| (3) parse が要素を返さず全観点から素通りする | 06 には並行レビュー機構が無いので、素通りしても気付く手段が無い | **要検討** — ECN-029 の導入が前提 |

**推奨**: 06 で残り5モジュールに `operations` を入れる際、
05 の ADR-012 と ECN-030 を先に読み、
「入口は `opts.kind` / `opts.id` で分岐する」「知らない field は無変化」
「id 認識の削除関数を入口から呼ぶ」の3点を最初から満たす。
後から直すと 05 と同じ12例を繰り返す。

## ECN-029 (並行レビュー機構) — 対象外 / 段階導入

06 には `tools/review/` に相当する仕組みが無い。
テストは 34ファイル (`tests/`) あり、`npm run test:all` で
ユニット + e2e が回る構成。

一度に22観点を持ち込むのは現実的ではないので、段階を提案する。

| 段階 | 内容 | 根拠 |
|---|---|---|
| 1 | **実描画オラクル** (`tests/render-oracle.js` 相当) | 05 では「テストが通っても図が壊れる」を最初に断ち切ったのがこれ。PlantUML はサーバ / ローカル両方のレンダラがあるので、どちらで描かせるかの決めが要る |
| 2 | **契約ベースのレビュアー R1 / R2 / R12** (破壊しない / 削除の巻き添え / 無言の空振り) | 契約導入と同時に入れれば、ECN-030 の12例を未然に防げる |
| 3 | **網羅率の計測とゲート化** | 観点が増えてから。先に入れても測る対象が無い |

**対象外とした理由**: 移植そのものは 06 側の作業計画に属し、
私の一存で 06 のリポジトリを変更するべきではない。
本分析は「該当する / しない」の判定までとする。
