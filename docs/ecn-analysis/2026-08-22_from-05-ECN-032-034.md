## 該当あり: A100 並べ替えが図の宣言行を巻き込む

**05 と同一のコードが `src/modules/sequence.js:1497` にある。**

    moveUp: function(text, lineNum) {
      if (lineNum <= 1) return text;
      return window.MA.textUpdater.swapLines(text, lineNum, lineNum - 1);
    }

### 実測 (2026-08-22)

title の無い文書 (利用者が title を消せば普通に起きる) で先頭の participant を上へ動かした。

    前                          後
    1: @startuml                1: actor User
    2: actor User          →    2: @startuml
    3: participant System       3: participant System

**`@startuml` が1行目から消える。PlantUML はこの文書を描けない。**

ひな形 (title あり) では `@startuml` は残るが、要素が `title` を飛び越える。

### 05 での直し方

要素が占める範囲ごと、**同じ種類の隣の要素と**入れ替える
(`window.MA.textUpdater.moveElementLine`)。05 では18モジュールに適用した。

### 06 での対応案

`operations` を持つのは `sequence` と `usecase` の2モジュールだけなので、
影響範囲は小さい。ただし **PlantUML は `@startuml` / `@enduml` で囲む構造**
なので、05 の「1行目だけ守る」では足りず、**囲みの内側だけで動かす**必要がある。

**この分析は提案であり、実装はしていない。**

### A104 人の速さで打つと1打鍵ごとに描き直す

**06 は既に対策されている。** `src/app.js:37`

    var RENDER_DEBOUNCE_MS = 150;
    renderTimer = setTimeout(refresh, RENDER_DEBOUNCE_MS);

05 は `requestAnimationFrame` だけで合流させていたため、200ms 間隔の打鍵で
1回も合流しなかった。**06 は固定150msの待ちがあるので、この欠陥は起きない。**

ただし 05 の実測では、**1回の描き直しが150msを超える規模では固定値が効かない**
(200要素で211ms、400要素で508ms)。06 で同規模の図を扱うなら、
05 と同じ「前回かかった時間から決める」形が要るかもしれない。**未実測。**
